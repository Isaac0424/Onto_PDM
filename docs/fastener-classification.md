# 볼트 형상 분류: CAD 모양으로 볼트 종류 판단하기

- 상태: 분류기 · 속성 후보 변환 · 뷰어 메시 읽기 API 구현 완료, 화면(속성 패널 · 품번 매칭 · 조립 규칙) 연결 완료(8장). **실제 STEP 4종(HCR 로봇)으로 검증했다(11장).**
- 코드: `web/src/extract/fastener.ts`(분류), `fastener.geometry.ts`(기하 계산), `fastener.config.ts`(비율표 · 임계값), `fastener.attributes.ts`(속성 후보 변환), `fastener.fixtures.ts`(시험용 메시 생성기), 시험 `fastener.test.ts`.
- OPMS 와의 관계: 클래스 이름 · `headType` 값은 OPMS 가 소유하고 PDM 은 읽기만 한다. 요청서는 [opms-request-bolt-shape.md](opms-request-bolt-shape.md).

## 1. 무엇을 하나

부품 하나의 삼각형 메시를 받아 **볼트 종류 후보**(클래스 · 점수 · 근거)와 **속성 후보**(머리 모양 · 구동부 · 나사 규격 · 길이 · 육각구멍 크기)를 만든다. 볼트로 보이지 않는 형상(판 · 상자 · 핀 · 막대 · 너트 · 와셔 · 머리가 양쪽에 있는 것)은 `null`이다.

```
부품 메시 ─▶ 회전축 ─▶ 단면 프로파일 ─▶ 볼트 게이트 ─▶ 머리 윤곽 · 단면 · 구멍 ─▶ 클래스 점수 ─▶ 속성 후보
(getPartGeometry)                                                              (FastenerResult)   (fastenerAttributes)
```

값은 모두 **사람이 확정하기 전의 후보**이고 추정으로 표시한다. 뽑은 값에는 근거와 신뢰도가 붙는다(OPMS 와 같은 원칙).

## 2. 알고리즘

입력은 월드 좌표의 삼각형 목록이다(색인이 있어도 없어도 된다). 임의 방향 · 위치 · 균일 배율이어도 같은 결과를 낸다.

| 단계 | 하는 일 | 구현 |
|---|---|---|
| ① 회전축 | 표면 **면적 가중 공분산**의 고유벡터. 축에 수직인 두 고유값이 같은 대칭 물체이므로, 가장 긴 축이 아니라 "나머지 둘과 따로 떨어진 고유값"의 방향을 축으로 쓴다(짧고 굵은 볼트나 와셔도 맞는다) | `findFrame` |
| ② 단면 프로파일 | 축에 수직인 평면으로 메시를 잘라 단면 선분을 얻고, 평면마다 외접 반지름 R(z)을 잰다. 전체를 96개 평면으로 훑은 뒤 머리 근처를 80개로 촘촘히 다시 본다 | `sectionAt`, `planeStat` |
| ③ 볼트 게이트 | 머리가 있고(최대 반지름 ≥ 1.3 × 몸통), 몸통이 고르고(±10% 안에 80%), 반대쪽 끝이 굵지 않고, 길이 · 머리 높이가 볼트 범위일 때만 통과 | `FASTENER_CONFIG.gate` |
| ④ 머리 단면 | 머리 몸체 중간 높이의 단면에서 중심으로 90개 광선을 쏴 바깥 윤곽 ρ(θ)를 읽는다. min/max 비 0.866 · 6차 조화 성분이 크면 육각, 거의 1이면 원 | `rayProfile`, `harmonic` |
| ⑤ 머리 윤곽 | 머리 높이를 0~1로 본 위치의 반지름 비로 **원뿔(접시)** · **돔(버튼)** · **플랜지** · **원통** 점수를 낸다(상호 배타 아님, 부드러운 구간 점수) | `profile` 설정 |
| ⑥ 윗면 구멍 | 머리 윗부분의 여러 평면에서 광선이 경계를 두 번 이상 만나는 비율이 크면 구멍이 있는 단면이다. 구멍 깊이의 40% 위치에서 안쪽 윤곽을 읽어 육각(대변 측정) · 별(Torx 형) · 십자 · 일자를 가른다 | `recessKind` |
| ⑦ 치수 | 나사 지름 d(몸통), 길이 L(머리 아래부터), 머리 지름/d · 높이/d | `geometry` |
| ⑧ 점수 | 클래스마다 윤곽 일치도 × 단면 일치도 × 비율 일치도(사다리꼴 구간의 기하평균, 바닥 0.15) × 구동부 확인 정도 | `scoreClass` |

나사산은 모델에 있어도 되고 없어도 된다. 나선형 요철이 있으면 평면마다 외접 반지름이 바깥지름(호칭 지름)을 그대로 준다.

**실제 STEP 검증(11장)에서 더한 단계**

| 단계 | 하는 일 | 구현 |
|---|---|---|
| ⑨ 호칭 지름 결정 | 실제 모델은 나사 몸통을 호칭 지름이 아니라 나사산의 **골지름**(D − 1.2269·P)으로 그리는 일이 흔하다(M4 볼트의 몸통이 3.14 mm). 잰 지름이 맞는 호칭 · 골지름 후보를 모두 만들어, 머리 치수(지름 · 높이)로 점수를 낸 뒤 가장 잘 맞는 호칭을 고른다. 호칭 몸통이 이기면 `nominal`, 골지름이 이기면 `minor` | `nominalOptions`, `FASTENER_CONFIG.thread` |
| ⑩ 머리만 있는 모델 | 몸통이 없고 머리(곧은 옆면의 기둥 + 윗면의 막힌 육각 구멍)만 있는 모델도 읽는다. 구멍이 있는 쪽이 윗면이고, 바닥 쪽은 막혀 있어야 하며(관통 구멍 = 너트 · 와셔), 호칭은 머리 치수에서 짐작하고(`head`) 길이는 만들지 않는다. 몸통이 없어 근거가 약하므로 **육각 구멍 확인 · 호칭 M24 이하 · 구멍 크기가 렌치 구멍 비율과 일치**를 모두 요구하고 신뢰도에 0.7을 곱한다 | `headOnlyBody`, `FASTENER_CONFIG.headOnly` |
| ⑪ 여러 몸체 | 같은 이름의 볼트 여러 개가 한 부품으로 합쳐진 모델은 먼저 전체로 보고(뚜렷하면 끝), 아니면 꼭짓점을 위치로 합쳐(weld) 서로 떨어진 덩어리로 나눠 덩어리마다 분류한다. 가장 많은 종류를 대표로 삼고 `bodies` 에 개수를 적는다 | `splitBodies`, `FASTENER_CONFIG.split` |
| ⑫ 오탐 막기 | 단면 중심이 한 축 위에 있지 않으면(흩어진 몸체) · 몸통이 52 mm 를 넘으면(단위가 분명한 파일만) · 후보가 없는데 머리 윤곽 × 단면이 어느 클래스와도 안 맞으면(커넥터 · 원통 부품) 볼트가 아니다 | `axisDrift`, `FASTENER_CONFIG.gate` |

## 3. 결과 모양

```ts
classifyFastener(mesh): FastenerResult | null
{
  candidates: [{ classCode, label, headType, score, proposed, evidence: string[] }],   // 점수 내림차순, 0.1 미만은 올리지 않음
  confidence,   // 1위 점수에서 2위와의 근접함만큼 깎은 값(0~0.95). 후보가 없으면 0
  ambiguous,    // 구동부 정보가 없거나 1·2위 점수 비가 0.6 이상
  driveType,    // 'HexSocket' | 'Torx' | 'Phillips' | 'Slotted' | 'ExternalHex' | null
  geometry,     // 나사 지름 · 머리 아래 길이 · 전체 길이 · 머리 지름 · 대변 · 머리 높이 · 윤곽 점수 · 육각 정도 · 구멍(모양 · 대변 · 깊이)
  unit,         // { known: 단위를 알아 mm 로 환산함, assumed: 파일에 단위가 없어 mm 로 가정함 }
  bodies,       // 한 부품 안에서 볼트로 읽힌 몸체 수(1 = 보통)
  headOnly,     // 몸통 없이 머리만 모델링됨(호칭은 머리 치수로 짐작, 길이 없음)
}
// geometry.nominalDiameter / diameterBasis: 표준 호칭 지름과 그 근거 ('nominal' 몸통 = 호칭, 'minor' 몸통 = 골지름, 'head' 머리 치수로 짐작)
```

근거 문장은 이런 꼴이다(소켓 헤드 M8×25).

```
머리 윤곽 원통형, 단면 원형
머리 지름/나사 지름 1.63(기준 1.45~1.95), 높이/나사 지름 1(기준 0.88~1.15)
윗면에 육각 구멍(대변 6 mm)
→ 소켓 헤드(추정)
```

**클래스 후보**: OPMS 의 `HexBolt`(Hex) · `HexFlangeBolt`(HexFlange) · `SocketHeadBolt`(Socket), 그리고 OPMS 에 **아직 없는** 제안 `ButtonHeadBolt`(Button) · `CountersunkHeadBolt`(Countersunk). 제안은 `proposed: true`이고 근거에 "OPMS 미등록 제안 클래스"가 붙는다. 화면에서는 "제안(미등록)"으로만 표시하고 OPMS 에 쓰지 않는다.

## 4. 속성 후보(`fastenerAttributes`)

| key | 값 | 신뢰도 | 비고 |
|---|---|---|---|
| `headType` | `Hex` · `HexFlange` · `Socket` · `Button` · `Countersunk` | 후보 신뢰도 | 근거에 다른 후보와 점수, 미등록 여부가 붙는다. 후보가 없으면 만들지 않는다 |
| `driveType` | `HexSocket` · `Torx` · `Phillips` · `Slotted` · `ExternalHex` | 0.8 (별 · 십자 · 일자 0.45, 외육각 0.7) | OPMS `driveType` 은 후속 요청이라 값만 먼저 맞췄다 |
| `threadSize` | `M{호칭}` (잰 지름을 표준 호칭 ±6%로 반올림, 골지름 몸통은 머리와 맞는 호칭) | 0.75 (골지름 0.7, 머리만 있는 모델 0.5, 표준과 안 맞으면 0.4) | "CAD 몸통 지름 8.0 mm → 표준 호칭 M8로 반올림" · "CAD 몸통 지름 3.14 mm = M4 나사산의 골지름 → 호칭 M4". 피치는 나사산이 모델에 없어 알 수 없다고 근거에 적는다 |
| `length` | mm (정수 · 0.5 mm 단위 규격 길이에 0.12 mm 안이면 맞춘다: 14.95 → 15) | 0.7 | 머리 아래 길이. **접시머리만 머리를 포함한 전체 길이**(규격의 길이 정의). **머리만 있는 모델은 만들지 않는다**. 근거에 잰 값과 맞춘 값을 적는다 |
| `socketSize` | mm | 0.65 | 육각 구멍의 대변 |

단위: 파일에 단위가 없으면(STL · OBJ 의 `'단위'` 자리표시) mm 로 가정하고 모든 치수를 추정으로 표시하며 신뢰도를 20% 깎고 근거에 "파일에 단위 정보가 없어 mm 로 가정"을 적는다(`cad.ts`의 `isUnitUnspecified` 규칙과 같다). cm · m · in 은 mm 로 환산하고, 모르는 단위는 치수 후보를 만들지 않고 머리 모양만 남긴다.

### extractCadAttributes 연결

`CadPartInput.mesh`(선택)가 있을 때만 분류를 돌려 위 후보를 더한다. 메시가 없으면 기존 동작 그대로다. 볼트로 판정된 부품에서는 **상자 크기 기반 길이 · 너비 · 높이 · 두께 후보를 뺀다**(머리까지 잰 값이라 규격의 길이와 다르고, 너비 · 높이는 머리 지름이어서 품번 매칭에 혼동을 준다). 이름의 규격 표기(`M8x25`)와 형상의 값은 둘 다 후보로 남아 사람이 비교한다.

## 5. 설정 객체와 비율표 (`fastener.config.ts`)

**참고치다. 표준 표로 검증하기 전까지는 참고치로만 본다.** 구간은 사다리꼴 `[0이 되는 하한, 1이 되기 시작, 1이 끝남, 0이 되는 상한]`이라 경계에서 점수가 끊기지 않는다(시험이 2% 걸음마다 점수가 0.2 넘게 뛰지 않음을 확인한다).

| 클래스 | 머리 윤곽 | 단면 | 폭 / d | 높이 / d | 구동부 |
|---|---|---|---|---|---|
| `HexBolt` (ISO 4014 · 4017) | 원통 | 육각 | 대변 1.45~1.85 (허용 1.30~2.05) | 0.52~0.85 | 구멍 없음 |
| `HexFlangeBolt` (ISO 4162 · 15072) | 아래 플랜지 + 위 육각 | 육각 | 플랜지 1.85~2.65, 대변 1.45~1.85 | 0.75~1.3 | 구멍 없음 |
| `SocketHeadBolt` (ISO 4762) | 원통 | 원 | 머리 1.45~1.95 | 0.88~1.15 | 육각 구멍 |
| `ButtonHeadBolt` (ISO 7380, 제안) | 돔 | 원 | 머리 1.65~2.05 | 0.42~0.66 | 육각 구멍 |
| `CountersunkHeadBolt` (ISO 10642, 제안) | 90° 원뿔 | 원 | 머리 1.88~2.45 | 0.48~0.78 | 육각 구멍 |

구동부 확인 정도(점수에 곱함): 육각 구멍 확인 1, 구멍은 있으나 모양 미상 0.7, 별 · 십자 · 일자 0.6, **구멍을 확인하지 못함 0.55**, 육각 머리 계열인데 구멍이 있음 0.4. 임계값(게이트 · 윤곽 · 육각 판정 · 구멍 판정)도 같은 파일에 있다.

> 요청서(opms-request-bolt-shape.md 5절)의 접시머리 머리 지름 비를 2.0~2.2로 적었는데, ISO 10642 의 이론 치수(M4 8.96, M6 13.44, M8 17.92)는 d 의 2.24배다. 설정은 1.88~2.45로 넓게 잡았다. 요청서 쪽 수치도 이에 맞춰 고치는 것이 좋다.

## 6. 정확도

절차적으로 만든 시험 볼트(표준의 대표 치수, 고리 72개 · 삼각형 800~2300개)로 **5종류 × 3규격(M4 · M6 · M8) × 3길이(10 · 25 · 60) = 45개를 모두 1위로 정확히 분류**한다(45/45). 나사 지름은 오차 2% 안, 길이는 0.25 mm 안, 육각구멍 크기는 0.05 mm 안이다.

| 종류 | M4 | M6 | M8 | 1위 클래스 | 구동부 |
|---|---|---|---|---|---|
| 육각 | 0.98 | 0.98 | 0.98 | `HexBolt` | ExternalHex |
| 육각 플랜지 | 0.98 | 0.98 | 0.98 | `HexFlangeBolt` | ExternalHex |
| 소켓 | 0.98 | 0.98 | 0.98 | `SocketHeadBolt` | HexSocket (2위 `ButtonHeadBolt` 0.11) |
| 버튼 | 0.98 | 0.98 | 0.98 | `ButtonHeadBolt` | HexSocket |
| 접시머리 | 0.98 | 0.98 | 0.98 | `CountersunkHeadBolt` | HexSocket |

점수는 길이 10 · 25 · 60에서 모두 같았다. 그 밖에 확인한 것:

- 임의 회전 · 이동 · 배율(0.1 · 3 · 25.4배)에서 같은 클래스 · 같은 비율. 색인 없는 삼각형 목록도 같은 결과.
- 나선형 나사산을 모델링한 볼트(M6 · M8)도 같은 종류 · 같은 호칭.
- 구멍 모양: 육각 · 별(Torx 형) · 십자 · 일자를 구분(후 셋은 점수를 낮게).
- 구동부 구멍을 뺀 단순화 모델: 윤곽이 남아 있으면 같은 클래스가 1위지만 점수 0.55 · `ambiguous` · 근거에 "구동부 구멍을 확인하지 못함". 윤곽까지 뭉개진 모델(버튼 비율의 납작한 원통)은 소켓 0.21 · 버튼 0.17처럼 여러 후보를 낸다(신뢰도 0.3 미만).
- 판 · 상자 · 핀 · 막대 · 너트 · 와셔 · 아령은 `null`. 빈 입력 · NaN · 삼각형 11개 이하도 안전하게 `null`.
- 성능: 삼각형 14만 개(나사산 모델) 약 0.1초, 21만 개 약 0.13초(jsdom 시험 환경).
- 실제 뷰어(Edge, OBJ · STL)로 올려 `getPartGeometry`로 읽은 메시를 분류했다: OBJ 5종 각각 정확히 분류, 볼트 5개 + 판 + 너트 어셈블리(OBJ · STL, STL 은 뷰어가 연결된 덩어리로 부품을 나눈다)에서 볼트 5개는 모두 맞고 판 · 너트는 `null`.

**한계(정확도를 말할 때 같이 말한다)**: 위 45/45 는 이 저장소가 만든 시험 형상에 대한 것이다. 실제 STEP(OCCT 로 삼각분할한 메시)로는 11장에서 따로 확인했고, 그때 찾은 현상(골지름 몸통 · 합쳐진 볼트 · 머리만 있는 모델 · 머리와 나사 끝 사이가 빈 모델 · 큰 부품 오탐)은 합성 변형으로 재현해 `fastener.real.test.ts` 에 회귀 시험으로 남겼다.

## 7. 한계

- **나사산이 없으면 피치 · 전나사/반나사는 알 수 없다.** `threadSize`의 피치는 OPMS 가 보통 나사 값으로 채운다. 나사산이 모델에 있어도 호칭 피치는 읽지 않는다(바깥지름만 쓴다).
- **단순화한 모델**(구동부 구멍을 생략): 구멍으로 가르는 소켓 · 버튼 · 접시머리는 윤곽으로만 구분하고 단정하지 않는다. 윤곽도 뭉개졌으면 후보 여러 개를 낮은 신뢰로 낸다.
- **강도 등급(8.8 · 12.9) · 재질 · 도금 · 피치는 형상으로 알 수 없다.** 사양서 · BOM 에서 온다.
- **STL · OBJ 는 부품 구분이 없을 수 있다.** STL 은 뷰어가 연결된 덩어리로 나누고, OBJ 는 객체 단위다. 하나로 합쳐진 조립체는 볼트로 판정되지 않는다.
- **분류 대상 밖의 머리**(팬 · 치즈 · 캐리지 · 아이 · 윙 · 안전 와이어 구멍 등)는 가까운 클래스로 억지로 나누지 않고 점수가 낮아 후보가 없을 수 있다. 그때도 나사 규격 · 길이는 남는다.
- **짧은 볼트**: 머리 아래 길이가 나사 지름의 절반보다 짧거나(예: 접시머리 M8×8) 전체 길이가 지름보다 짧으면 볼트로 보지 않는다. 머리 지름이 몸통의 1.3배 미만인 것(스터드 · 육각 막대)도 아니다.
- 별(Torx) · 십자 · 일자 구멍 판별은 단순한 반지름 비 · 조화 성분 규칙이라 실제 형상에서는 흔들릴 수 있다. 낮은 신뢰로만 낸다.
- 뾰족한 끝(포인트) · 머리 아래 목(neck) · 와이어 구멍은 읽지 않는다.
- **머리만 있는 모델**은 소켓 · 버튼(곧은 옆면 또는 돔)만 읽는다. 접시머리(원뿔)는 옆면이 곧지 않아 지원하지 않고, 육각 구멍이 확인되지 않거나(별 · 십자 포함) 짐작한 호칭이 M24 를 넘으면 볼트로 보지 않는다. 길이는 알 수 없다.
- **여러 몸체**: 삼각형이 12000 개를 넘는 부품은 나누지 않는다(볼트 묶음이 아니라 큰 부품). 덩어리가 64 개를 넘어도 나누지 않는다. 종류가 섞이면 가장 많은 종류를 대표로 삼는다(나머지 종류는 근거에 개수만 남는다).
- 골지름으로 그린 몸통의 호칭 판단은 보통 나사(coarse) 피치 표를 쓴다. 가는 나사(fine)의 골지름은 따로 보지 않는다.

## 8. UI 연결 (완료: 작업 U, 실제 OPMS 매칭까지 11장에서 확인)

이 장은 연결 설계였고 지금은 구현돼 있다(`web/src/pages/studio/`의 `FastenerBlock` · `useFastenerShapes` · 속성 패널 · 품번 매칭). 연결은 이렇게 했다.

1. **메시 읽기**: 부품을 선택할 때(또는 분석 시작 시) 뷰어 `studio.getPartGeometry(partId)`로 메시를 읽는다(아래 9장). `CadPartInput.mesh`에 넣어 `extractCadAttributes`를 부르면 후보가 속성 패널의 기존 흐름에 섞여 들어온다.
2. **속성 패널**: `headType` · `driveType` · `threadSize` · `length` · `socketSize` 후보가 기존 후보 칩처럼 나온다(근거 문장은 이미 하나로 합쳐져 있다). 클래스 후보 목록(`candidates`)은 별도 칩 줄로 보여준다: 점수 · `proposed`면 "제안(미등록)" 표시 · 근거 펼치기. `ambiguous`면 "구동부 구멍을 확인하지 못해 단정하지 않았어요" 안내.
3. **품번 매칭**: 사람이 확정한 `headType` · `threadSize` · `length` 등이 OPMS 품번 매칭의 검색 조건이다. 확정 전에도 충분히 확실한 추정 규격은 "후보 · 추정"으로 찾는다(12장). 예: "M8 · 25 mm · 육각구멍붙이볼트".
4. **조립 규칙 분류기 입력**: `web/src/api/mock/assemblyRules.ts`의 클래스 분류에 형상 분류 결과를 클래스 후보로 넘긴다(이름이 `볼트`가 아니어도 육각구멍붙이볼트로 분류, 토크 렌치 같은 규칙이 붙는다).
5. **비용**: 부품당 약 10 ms 이하(작은 메시)라 부품이 많은 CAD 에서는 볼트로 보이는 부품(이름 · 크기 필터)만 돌린다.

## 9. 뷰어 API: `getPartGeometry`

뷰어(`explode-studio`)는 부품의 삼각형 메시를 안에서만 갖고 있어서 읽기 전용 메서드를 하나 더했다(`tools/build_module.py`의 API 템플릿 → `src/studio.js` 재생성, `src/index.d.ts`, `README.md`).

```ts
studio.getPartGeometry(nameOrId: string | number): PartGeometry | null
interface PartGeometry { name: string; unit: string; positions: Float32Array; indices?: Uint32Array }
```

- `positions`는 x y z 꼭짓점, `indices`는 삼각형 꼭짓점 번호(없으면 9개씩이 삼각형 하나). 부품이 여러 메시로 이뤄졌으면 하나로 합쳐 준다.
- 복사본이라 바꿔도 장면에 영향이 없다. `unit`은 `mm` · `cm` · `m` · `in` 또는 `'단위'`(STL · OBJ 처럼 단위가 없는 파일).
- 분류기에 그대로 넘긴다: `classifyFastener({ positions, indices, unit })`.

## 10. OPMS 가 반영된 뒤 바꿀 것

1. 클래스 이름 · `headType` 값은 OPMS 에서 읽는다(OPMS API 또는 스냅샷). `FASTENER_CLASSES`에서 `classCode` · `label` · `proposed`를 OPMS 값으로 바꾸고, OPMS 에 생긴 클래스는 `proposed: false`로 만든다.
2. 비율표(5장)는 OPMS 에 기하 규칙 유형이 없는 한 PDM 분류기 설정으로 남는다. 형식은 OPMS YAML 과 비슷하게 두었으니, 나중에 OPMS 에 새 규칙 유형이 생기면 옮긴다.
3. `driveType`이 OPMS 에 생기면 `DriveCode`를 그 값과 맞춘다.
4. 이 문서 5장 아래의 접시머리 비율 정정을 요청서에 반영한다.

**홀드아웃에 대해 솔직히**: 여러 몸체 · 머리만 있는 모델 · 전체 우선 · 커넥터 오탐은 12A 로 설계했고, 골지름은 3A · 5A 에서 본 현상을 ISO 표로 구현한 것이라 12A 는 그 규칙의 회귀 확인이다. 머리만 있는 모델의 오탐 2건은 3A · 5A 검증에서 나와 고쳤으므로 3A · 5A 는 그 규칙에 대해 엄밀한 홀드아웃이 아니다. 컨트롤러(볼트 0개)는 끝까지 손대지 않은 대조군이고 전후 오탐이 모두 0 이다.

### 11.5 끝에서 끝까지: 실제 OPMS 매칭

실제 12A STEP → 스튜디오(http 모드) → 부품 선택 → 종류 · 나사 규격 · 길이 확정 → PDM 백엔드(포트 8100) → OPMS Neo4j(읽기 전용, 온톨로지 0.15.0). 백엔드 호출은 `status` · `classes` · `parts` · `match`(읽기)뿐이고, 서버 DB · 보관소(8788)는 가로채 실제 DB 에 쌓이지 않게 했다. OPMS 시연 기대표 `R04`(PDM 이 CAD 값만으로 물을 때 = R05 열)와 같다.

| CAD 부품 | R04 기대 | 실제(스튜디오에 나온 것) |
|---|---|---|
| `BOLT-M3X8` | 후보 R01-1 | 후보 1개: `P-00000000046` 육각구멍붙이볼트 M3 · 8 mm · SCM435 |
| `BOLT-M3X15` | 후보 R01-2 | 후보 1개: `P-00000000049` M3 · 15 mm · SCM435 |
| `BOLT-M4X15` | 후보 2개(R01-4 · 5) | 후보 2개: `P-00000000048`(SUS304) · `P-00000000050`(SCM435), 모두 M4 · 15 mm |
| `BOLT-M4`(길이 없음, 머리만) | 후보 3개(R01-3 · 4 · 5) | 후보 3개: `P-00000000047`(M4 · 10) · `048` · `050` |
| `BOLT-M4X25` | 미매칭 | 후보 없음(분류만 육각구멍붙이볼트) |

화면의 온톨로지 그래프에 OPMS 부품의 분류 경로(기계 부품 › 체결 부품 › 볼트 › 육각구멍붙이볼트)와 재질 · 강도 등급 · 표면처리 · 육각구멍 크기가 보였다. 한 가지 보이던 흠: 길이가 없는 머리만 있는 모델(`BOLT-M4`)도 규격만 비교하고 "100 % 일치"라고 표시했다(백엔드 임시 매칭이 양쪽에 값이 있는 속성만 비교하기 때문). → 12장에서 후보 표시를 "확인한 K개 속성이 모두 일치 · 미확인 M개(…)"로 바꿔 고쳤다.

### 11.6 남은 한계

- 표본은 한 제조사의 로봇 한 계열이라 **모두 소켓 헤드**다. 육각 · 버튼 · 접시 · 플랜지 머리의 실제 STEP 정확도는 확인하지 못했다(이 STEP 들에 없다). 그 종류는 여전히 시험 형상(45/45)에만 근거한다.
- 12A 의 59개는 종류를 이름 · ISO 치수로 확인했다(11.2).
- 3A `HCR3A_BASE_COVER_BOLT_1` 4개(두 몸체: 지름 3 × 6 핀과 머리 지름 6 · 높이 1.7 의 볼트)는 접시머리 0.60 · 십자 구멍으로 읽힌다. 정답을 알 수 없어 채점하지 않았고 신뢰도는 낮다.
- 컨트롤러 STEP 에는 볼트가 없다(OPMS 시연 문서가 말한 `FLAT HEAD CAP SCREW M3*6` 문자열도 이 파일에는 없다).
- 머리만 있는 접시머리 · 구멍 없는 머리만 모델은 읽지 않는다(7장). 피치 · 전나사/반나사 · 강도 등급 · 재질은 형상으로 알 수 없다.
- 삼각형이 많은 큰 부품이 볼트 묶음일 때(12,000 개 초과)는 나누지 않는다.

## 12. 추정 규격으로 보유 품번 찾기 (확정 전, 2026-11-12)

문제: 분류기는 종류 · 나사 규격 · 길이를 이미 만드는데, 품번 매칭은 **사람이 확정한 값**만 입력으로 써서 확정 전에는 모든 부품이 "규격 확정 필요"로 남았다. 12A 에는 같은 볼트가 수십 개라 부품마다 확정하게 할 수 없다.

### 12.1 동작

- **조건**(`fastener.estimate.ts`의 `estimateFastener`, 문턱은 `fastener.config.ts`의 `autoMatch.minScore`): 1위 후보 점수 ≥ **0.6**, `ambiguous` 가 아님(1·2위가 가깝거나 구동부를 못 읽은 모델 제외), 단위를 알고 표준 호칭의 나사 규격이 있음. 0.6 은 머리만 있는 모델의 하한(`headOnly.minScore`)과 같고, 실제 STEP 에서 정답 볼트의 1위 점수가 대부분 그 이상이다.
- **입력**: 클래스(OPMS 에 있는 분류만) · 머리 모양 · 나사 규격 · 길이(머리만 있는 모델은 길이 없음). **사람이 확정한 값이 추정 값보다 우선**하고, 사람이 제외한 추정 후보(나사 규격 · 길이)는 쓰지 않는다. 사람이 고른 볼트 종류는 추정 클래스를 덮어쓴다.
- **표시**: 결과는 늘 **후보**다. 부품 줄 칩 "후보 N개 · 추정" / "후보 P-… · 추정", OPMS 에 같은 규격이 없으면 "미보유 · 추정 규격". 어떤 API 가 확정(matched)을 돌려줘도 후보(suggested)로 둔다 — **품번 확정은 늘 사람이 한다**. 사람이 규격(나사 규격 · 길이)을 확정하면 그 값의 "추정" 표시가 사라진다. 온톨로지 탭에는 후보 목록 위에 "CAD 형상에서 M4 · 15 mm 로 추정해 찾았어요. 규격을 확정하면 더 정확해져요"(단위 없는 파일은 "mm 로 가정한 값" 덧붙임).
- **추정하지 못한 부품**(볼트가 아님, 구멍을 못 읽은 단순화 모델, 점수 낮음): "규격 확정 필요"(툴팁 "CAD로 규격을 추정하지 못했어요 — 속성 탭에서 확정하면 찾아요"). 형상 분석이 끝나지 않은 부품은 "형상 분석 중…"이다(같은 이름은 처음 나온 부품의 크기로 미리 분석 여부를 정하고, 화면 표시도 같은 규칙을 쓴다 — 실제 12A 에서 본 "분석 중이 끝나지 않는" 문제의 원인이었다).
- **조립 규칙**에는 추정으로 찾은 후보의 분류를 쓰지 않는다(확정한 클래스만).

### 12.2 성능과 요청 수

- 같은 (클래스 · 머리 모양 · 나사 규격 · 길이)는 OPMS 에 **한 번만** 묻고 결과를 나눠 쓴다(`httpApi` 의 요청 중복 제거 · 진행 중 요청 공유 · OPMS 를 못 읽은 결과는 기억하지 않음). 규격이 바뀐 부품만 다시 묻는다.
- 동시 요청 최대 4개, 고른 부품이 먼저, 끝나는 대로 화면에 반영(`useSpecMatches`). OPMS 연결 상태를 확인하는 동안과 연결이 안 될 때는 묻지 않는다. CAD 를 바꾸거나 OPMS 연결이 돌아오면 기억한 결과를 비운다(`clearMatchCache`).
- **실제 12A STEP 확인**(Playwright · Edge, 서버 DB · 보관소는 가로챔, OPMS 는 읽기만): 부품 이름 29종(볼트 부품 77개 중 이름이 같은 것은 묶임), 확정 없이 볼트 이름 7종이 모두 "후보 · 추정"(후보 5 · 미보유 · 추정 규격 1), 나머지 하우징 · 커넥터 22종은 "규격 확정 필요". **OPMS 로 나간 매칭 요청은 5개**(M3×8 · M3×15 · M4×15 · M4(길이 없음) · M4×25)이고 모델이 열린 뒤 약 0.4 초 안에 모두 나갔다. 형상 분석이 끝나는 데 모델을 연 뒤 약 5 초. 결과는 OPMS 시연 기대표(R04)와 같다(M3×8 → P-…046, M3×15 → P-…049, M4×15 → 2개, M4 → 3개, M4×25 → 없음).

### 12.3 후보의 일치 표시 (퍼센트 → 확인한 속성)

백엔드 임시 매칭의 점수는 **양쪽에 값이 있는 속성만** 비교한다. 그래서 길이가 없어도 규격만 같으면 100 % 가 되어 완전 일치로 오인됐다. 후보 한 줄의 주 표시를 바꿨다.

| 상황 | 표시 |
|---|---|
| 확인한 속성이 모두 일치, 미확인 없음 | `확인한 K개 속성이 모두 일치` |
| 확인한 속성이 모두 일치, 미확인 있음 | `확인한 K개 속성이 모두 일치 · 미확인 M개(길이, 재질 …)` |
| 불일치가 있음 | `확인한 K개 중 H개 일치 · 미확인 M개(…)` |
| 응답에 비교한 속성 정보가 없음 | `N% 일치` (그때만) |

가중 점수 퍼센트는 툴팁에만 둔다. 미확인이 하나라도 있으면 본문 어디에도 "100% 일치"라고 쓰지 않는다(온톨로지 탭의 "상태" 줄도 퍼센트 없이 "규격 일치(나사 규격 · 길이 · 머리 모양)").

### 12.4 한계

- 추정이 틀릴 수 있다(예: 파일에 단위가 없는 OBJ · STL · GLB 는 mm 로 가정 — 추정 안내에 적는다). 그래서 확정이 아니라 후보 · 추정으로만 보인다.
- 머리만 있는 모델은 길이 없이 나사 규격만으로 찾아 후보가 많아진다(M4 → 3개). 길이는 사람이 확정해야 좁혀진다.
- 분류기가 볼트 계열만 지원해서 판 · 커버 · 하우징 같은 부품은 여전히 "규격 확정 필요"다(찾을 규격을 형상에서 만들 수 없다).
- 매칭 판정은 백엔드 임시 구현이다(OPMS match API 가 열리면 교체).

## 13. OPMS 필수 속성 체크리스트 (속성 검증)

형상 분류가 만든 속성 후보가 **그 분류가 요구하는 필수 속성**을 얼마나 채웠는지 속성 탭에 보인다(`web/src/pages/studio/requiredAttrs.ts` · `RequiredBlock.tsx` · `useClassSpec.ts`). 판단은 OPMS 가 준 규칙으로만 한다(PDM 은 읽기만 한다).

**읽는 곳**: 백엔드 `GET /api/v1/pdm/opms/classes/{code}` 의 유효 속성 — 필수 여부(`required`) · 값 범위(`min` · `max`) · 고정 값(`fixed`) · 관례로 채워지는 값(`omitted_default`: 원문에 없으면 OPMS 가 채우는 개념, 예 나사 방향 → 오른나사 · `lookup_default`: 값 표의 기본 열, 예 피치 = 나사 규격별 보통 나사 값). 웹은 `PdmApi.opms.getClassSpec(code)`로 분류별 한 번만 읽는다.

**상태 4가지**(우선순위 순서):

| 상태 | 뜻 | 세는 법 |
|---|---|---|
| 확정 | 사람이 확정한 값(확정이 추정보다 우선) | 확인 |
| 추정 | 확정 전 후보. 출처에 따라 "CAD 추정" · "이름에서 추정"(같은 신뢰도면 CAD 가 먼저) | 확인이 아님("추정 N개"로 따로) |
| OPMS가 채워요 | 분류의 고정 값 · `omitted_default` · `lookup_default`(나사 규격이 정해져 있을 때만; 추정 규격이면 "다시 확인해요") | 확인(비어 있다고 세지 않는다) |
| 미확인 | 비어 있음. 재질 · 표면처리 · 강도 등급은 "CAD로 알 수 없어요 — 사양서·BOM에서 와요. 지금은 등록 요청 때 OPMS 검토 화면에서 채워요", 그 밖은 "CAD에서 읽지 못했어요" | 미확인 M개(이름 목록) |

제목은 "OPMS 필수 속성 · 확인 K/N"(K = 확정 + OPMS가 채워요, N = 필수 속성 수)이고, 요약은 매칭 후보 줄의 "미확인 M개(길이, 재질)"와 같은 말투다(`확인 2/8 · 추정 3개 · 미확인 3개(재질, 표면처리, 강도 등급)`). 목록은 확정 → 추정 → OPMS가 채워요 → 미확인 순이라 비어 있는 것이 아래에 모인다.

**값 범위**: OPMS `min` · `max` 에 걸리면 호박색 확인 칩("OPMS 기준(≥3 mm)보다 작아요", 추정이면 " · 추정이라 다시 확인해요"). 빨강은 쓰지 않는다(오류가 아니라 확인 필요).

**분류 고르기**: 사람이 확정한 볼트 종류가 먼저이고, 없으면 `estimateFastener` 가 추정한 분류. OPMS 에 없는 제안 분류(버튼헤드 · 접시머리)는 OPMS 에서 규칙을 읽을 수 없어 **상위 분류(볼트) 기준**이라고 밝히고(등록되면 필수 속성이 더 생길 수 있다) 확인한다. 분류를 정하지 못한 볼트(구멍을 못 읽은 단순화 모델)는 "볼트 종류를 확정하면 OPMS 필수 속성을 확인해요", OPMS 를 못 읽으면 "OPMS에 연결되면 필수 속성을 확인해요", 볼트가 아닌 부품에는 블록이 없다.

**흐름**: 미확인 필수 속성은 OPMS 분류 등록 요청 초안(`registrationDraft.ts`)의 `missingRequired` 와 notes 에 실려, 요청을 받는 쪽이 "무엇을 OPMS 검토 화면에서 채워야 하는지" 안다.

**실제 OPMS 확인**(2026-11-12, 12A STEP): `BOLT-M4X15` 를 고르면 실제 `SocketHeadBolt`(온톨로지 0.15.0)의 필수 8개(길이 ≥3 · 육각구멍 ≥1.5 · 재질 · 표면처리 · 피치 · 나사 방향 · 강도 등급 · 나사 규격)가 나오고, 확정 전 "확인 2/8 · 추정 3개 · 미확인 3개(재질, 강도 등급, 표면처리)", 나사 규격 · 길이 · 종류를 확정하면 "확인 4/8"이다. 실제 STEP 에서는 나사 규격 · 길이가 부품 이름(`BOLT-M4X15`)에서도 읽혀 "이름에서 추정"으로 표시된다(CAD 형상 값과 같다). 분류 상세는 `classes/SocketHeadBolt` 한 번만 읽었다.

한계: 필수 속성 이름은 OPMS 가 주는 대로 보이지만, "CAD로 알 수 없는 속성" 안내 목록(재질 · 표면처리 · 강도 등급)은 이 모듈의 상수다. 사양서 · BOM 올리기가 없어 미확인 값을 PDM 안에서 채울 길은 없다(등록 요청 때 OPMS 검토 화면).
