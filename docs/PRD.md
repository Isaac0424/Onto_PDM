# Onto PDM — 제품 요구사항 (PRD)

| 항목 | 내용 |
|---|---|
| 버전 | v0.1 초안 (2026-11-11) |
| 상태 | 검토 대기. 12장의 열린 질문에 답이 정해지면 v0.2 |
| 한 줄 요약 | 연구개발한 제품의 **CAD · BOM · 사양서**를 버전과 함께 관리하고, **3D 위에서 조립 순서와 사내 규칙을 안내**하며, 부품을 **OPMS 부품 마스터의 품번과 연결**해 제조(MES)로 넘기는 시스템 |
| 관련 문서 | [pdm-design.md](pdm-design.md)(기능 · DB · API) · [assembly-rules-spec.md](assembly-rules-spec.md)(조립 규칙) · [neo4j-lpg-design.md](neo4j-lpg-design.md)(그래프 모델) · [backend-plan.md](backend-plan.md)(백엔드) |

표기: ✅ 있음(목 데이터로 동작) · 🟡 일부 · ⬜ 없음. 우선순위: **P0** 첫 출시에 필수 · **P1** 이어서 · **P2** 나중.

## 1. 배경과 문제

- 연구개발팀이 만든 CAD, BOM, 사양서가 흩어져 있고, 어느 것이 최신 · 승인본인지 알기 어렵다.
- 설계에 쓴 부품이 회사가 이미 보유한 품번과 같은 것인지 사람이 일일이 대조한다. 같은 부품이 다른 이름으로 중복 등록된다.
- 제조 현장은 CAD와 BOM만으로는 **어떤 순서로, 무엇에 주의해서** 조립해야 하는지 알 수 없다. 이 지식은 숙련자의 머릿속이나 문서에 흩어져 있다. 용접 조건, 체결 토크, 포트 방향 같은 규칙이 대표적이다.
- 이 지식을 온톨로지로 정리해 두면, 부품과 공정에 규칙을 **자동으로 적용**하고 회사의 방식을 일관되게 따를 수 있다.

## 2. 목표와 비목표

### 목표
1. CAD · BOM · 사양서를 **제품 기준으로 묶어** 버전 관리한다.
2. CAD와 사양서에서 **속성을 뽑아**(11장) 보유 품번과 자동 매칭하고, 없는 부품은 OPMS에 등록을 요청한다.
3. CAD 3D 위에 **제조(조립) 순서와 사내 규칙**을 영화 속 시스템 화면처럼 겹쳐 보여 준다.
4. **제품 → 조립품 → 부품**의 연결을 3D 그래프로 보고, 규칙도 같은 방식으로 둘러본다.
5. 승인된 제조 BOM과 작업표준을 **MES로 발행**한다.

### 비목표 (이번 범위 밖)
- 구매 · 재고 · 원가 계산(ERP의 일), 설비 제어와 실적 수집(MES의 일)
- CAD 모델링과 편집 (보기와 분석만 한다)
- 부품 마스터 자체의 관리(품번 발급 · 분류체계는 **OPMS**가 소유한다)
- 인증/로그인 체계 (당분간 데모 사용자. 인증은 별도 과제)

## 3. 사용자와 대표 시나리오

| 사용자 | 하는 일 |
|---|---|
| 설계 엔지니어 | CAD · BOM · 사양서를 올리고, 부품 매칭을 확인하고, 등록을 요청한다 |
| 공정(생산기술) 엔지니어 | 조립 순서와 규칙 적용을 검토하고, 작업표준을 확정해 MES로 보낸다 |
| 관리자(승인자) | 리비전 · 등록 요청 · 분류 제안을 승인한다 |
| 현장 작업자 (MES 단말) | CAD 위의 단계별 안내를 보며 조립한다. 이 시스템이 직접 쓰는 사람은 아니고, 안내 화면의 시안이 여기서 나온다 |

**시나리오 A: 새 제품 올리기** — 엔지니어가 STEP · BOM 시트 · 사양서를 올린다 → 시스템이 구조와 치수를 분석한다 → 부품 12종 중 2종은 "보유", 2종은 "후보", 8종은 "미보유"로 나온다 → 후보를 확정하고 미보유 8종의 등록을 OPMS에 요청한다.

**시나리오 B: 조립 안내 확인** — 공정 엔지니어가 3D에서 단계를 넘기며 본다 → "제어 기판" 단계에서 "입력 포트는 왼쪽, ESD 스트랩 착용" 카드와 자막이 뜬다 → 커버 단계에서는 두께로 계산한 "필요 나사 길이 ≥ 7.5mm, 사용 M3×12 ✓"가 뜬다 → 승인한다.

**시나리오 C: 제품 연결 보기** — 제품을 열면 3D 그래프에 제품 → 조립품 → 부품이 연결되어 뜬다 → 부품을 누르면 그 부품의 CAD · BOM · 사양서 · 적용 규칙이 오른쪽에 묶여 나온다.

## 4. 시스템 경계와 데이터 소유

```
        ┌───────────── Onto PDM ─────────────┐        ┌─── OPMS ───┐
CAD ───▶│ 분석 · 보관 · 버전 · 조립 규칙 · 3D │── 등록 요청 ──▶│ 부품 마스터  │
BOM ───▶│                                    │◀─ 품번 · 분류 ─│ (Neo4j)     │
사양서 ─▶│                                    │                └────────────┘
        └──────────────┬─────────────────────┘
                       │ 제조 BOM + 작업표준 + CAD
                       ▼
                     MES  ──실적 · 불량──▶ (PDM으로 환류, P2)
```

| 데이터 | 소유 | 비고 |
|---|---|---|
| 품번 · 분류체계 · 재료 · 규격 속성 | **OPMS** (Neo4j) | PDM은 읽고, 없으면 등록을 **요청**한다. 충돌하면 OPMS를 따른다 |
| 파일 원본(CAD · BOM · 사양서) | PDM 파일 보관소 | sha256 이름. OPMS와 폴더를 공유(읽기 전용) |
| 리비전 · BOM 줄 · 문서 연결 · 등록 요청 | PDM (PostgreSQL) | [pdm-design.md](pdm-design.md) |
| 조립 규칙 · 조립 공정 | PDM, 온톨로지(Neo4j) | OPMS의 YAML → 컴파일 방식을 따른다 |
| 그래프 사본 | Neo4j `PdmItem` 등 | 승인본만 발행 ([neo4j-lpg-design.md](neo4j-lpg-design.md)) |

### 6.3 연결 그래프 (3D) — 신규

제품을 기준으로 사용되는 조립품과 부품이 **연결되어 보이는 3D 그래프**. 현재 디자인(밝은 글래스 + 홀로그램 시안)에 맞춘다.

| ID | 요구 | 우선 |
|---|---|---|
| F-GRF-1 | 제품을 가운데 두고 조립품 · 부품을 BOM 관계(수량 표시)로 잇는 3D 그래프를 그린다. 계층 단계가 한눈에 보이게 배치한다 | P0 ✅ |
| F-GRF-2 | 노드 색 · 모양으로 **상태**를 구분한다: 보유 / 후보 / 미보유, 조립품 / 부품 / 규격품. **규칙이 연결된 부품**은 표식을 단다 | P0 ✅ (리비전 상태 기준) |
| F-GRF-3 | 노드를 누르면 오른쪽에 **묶음 패널**: 품번 · 분류 · CAD · BOM · 사양서 · 적용 규칙 · 재고 | P0 ✅ (재고 제외) |
| F-GRF-4 | 끌어서 회전, 휠로 확대. **오른쪽 버튼 이동 · 브라우저 메뉴는 끈다**(CAD 화면과 같게) | P0 |
| F-GRF-5 | 필터: 단계(깊이), 상태, 공정 종류. 검색해서 노드로 이동 | P1 ✅ |
| F-GRF-6 | 같은 부품이 여러 곳에 쓰이면 한 노드에서 여러 상위로 잇는다(역전개 강조) | P1 🟡 사용처 경로 칩. 3D 경로 색 강조는 아직 |
| F-GRF-7 | 3D를 못 쓰거나 키보드만 쓸 때를 위한 **목록(트리) 보기**를 함께 제공한다 | P0 ✅ |
| F-GRF-8 | 노드 수가 많아도(기준 2,000개) 끊기지 않게 한다. 넘으면 단계를 접는다 | P1 |

기술 후보: 이미 쓰는 three.js 위에 3D 힘 기반 배치(`d3-force-3d`, 새 의존성)를 올린다. 규칙 화면의 온톨로지 보기도 **같은 그래프 컴포넌트를 재사용**한다.

### 6.4 조립 규칙 — 신규

| ID | 요구 | 우선 |
|---|---|---|
| F-RUL-1 | **규칙 목록**: 번호, 이름, 공정, 적용 분류, 핵심 값, 주의사항 수, 출처 문서, 상태. 검색 · 필터(공정 · 분류) | P0 ✅ |
| F-RUL-2 | **규칙 상세**: 조건 · 값(조건표 포함) · 주의사항 · 공구 · 출처, 그리고 **어느 제품 · 단계에서 쓰였는지** | P0 🟡 품목까지 |
| F-RUL-3 | **온톨로지로 보기**: 규칙 ↔ 공정 · 분류 · 공구 · 주의사항 연결을 3D 그래프로 본다 | P0 ✅ |
| F-RUL-4 | 규칙은 부품 **이름이 아니라 분류와 속성**에 붙는다. (분류가 없는 규칙은 이름 매칭으로 남아 있다) | P0 🟡 |
| F-RUL-5 | 규칙을 OPMS 방식으로 **YAML → 컴파일 → Neo4j**에 올리고 버전을 둔다 | P1 |
| F-RUL-6 | 규칙 **검증**: 같은 분류에 겹치는 규칙, 값이 비는 조건표, 출처 없는 규칙을 찾는다 | P1 ✅ |
| F-RUL-7 | 규칙 **편집 흐름**: 초안 → 검토 → 승인 → 폐기 (리비전과 같은 모양) | P2 |
| F-RUL-8 | 작업표준서(PDF)를 올리면 규칙 **후보**를 뽑고 사람이 확정한다 | P2 |

사양: [assembly-rules-spec.md](assembly-rules-spec.md). 현재 가상 규칙 8개(체결 · 커버 · 기판 · 스페이서 · 배터리 · 버튼 · 용접 · 압입).

| F-REV-1 | 작업중 → 검토 → 승인 → 폐기. 작업중 · 검토중은 작성자와 관리자만 보고, **승인본만 공개 · 발행** | P0 | ✅ |
| F-REV-2 | 설계변경(요청 → 영향 분석 → 지시): 바뀐 부품이 쓰인 제품 · 규칙을 보여 준다 | P2 | ⬜ |

## 7. 데이터와 온톨로지

- **PostgreSQL**: 품목 · 리비전 · BOM · 문서 · 등록 요청 · 감사 로그 (26개 표, [db/schema.sql](../db/schema.sql)).
- **Neo4j**(OPMS와 공유): OPMS의 `Class` `Concept` `Part`는 읽기만, PDM은 `PdmItem` `ItemRevision` `ProductModel` 등 자기 라벨에만 쓴다. `(:PdmItem)-[:OF_PART]->(:Part)`로 연결.
- **조립 규칙**: 공정 · 규칙 · 조건 · 값 · 주의사항 · 공구를 온톨로지로 두고, 분류(`Class`)에 `APPLIES_TO`로 건다.
- 품번 형식은 OPMS와 같은 `P-` + 숫자 11자리.

## 8. 비기능 요구

| 영역 | 요구 |
|---|---|
| **디자인** | OPMS 디자인 토큰 · 셸을 따른다. 밝은 글래스모피즘 위에 시안색 홀로그램 포인트. 3D 화면도 밝은 톤으로 통일 (CAD 화면만 어둡지 않게) |
| 조작 | 3D에서 오른쪽 버튼 이동 · 브라우저 메뉴 · 기준 축 같은 **의도하지 않은 표시를 만들지 않는다**. 왼쪽 드래그 = 회전, 휠 = 확대 |
| 색 사용 | 빨강은 오류 · 위험에만 쓴다. 경고는 호박색(노랑 계열), 정상은 초록, 후보는 주황 |
| 성능 | 3D 초당 30프레임 이상(기준 노트북). CAD 분석은 백그라운드로 하고 진행을 보인다 |
| 접근성 | 3D의 모든 정보는 목록으로도 볼 수 있다. 키보드로 단계 이동. 모션 줄이기 설정을 따른다 |
| 보안 · 권한 | 승인 전 리비전은 작성자 · 관리자만. 행 단위 권한은 DB에서 강제([roles.sql](../db/roles.sql)). 올린 파일은 형식 · 크기 검사 |
| 감사 | 누가 언제 무엇을 승인 · 변경했는지 남긴다 |
| 반응형 | 모바일 폭에서 가로 스크롤이 생기지 않는다 |
| 시험 | 단위 · 화면 · 실제 브라우저(E2E) 시험으로 위 요구를 고정한다 |

## 9. 화면 구성 (요약)

- **CAD 스튜디오**: 왼쪽 3D(밝은 글래스 프레임, 위 띠에 모델 이름과 상태), 오른쪽에 제조 순서 · 온톨로지 패널. 3D 안에 안내 카드(오른쪽)와 자막(아래).
- **연결 그래프**: 가운데 3D 그래프, 오른쪽에 묶음 패널, 위에 필터, 아래에 범례 · 목록 보기 전환.
- **규칙 목록**: 왼쪽 목록과 필터, 오른쪽에 상세. 상세 안에 "온톨로지로 보기" 3D 그래프.

## 11. 속성 추출: 무엇이 되고 무엇이 안 되는가

**결론: 일부는 지금 되고, 일부는 사람이 확정해야 하며, 일부는 아직 안 됩니다.** 원칙은 OPMS와 같다: **원문에 없는 값은 채우지 않는다.** 뽑은 값에는 출처(어느 파일 · 어느 구절 · 어느 부품)와 신뢰도를 붙이고, 사람이 확정한다.

### CAD (STEP)에서

| 속성 | 상태 | 비고 |
|---|---|---|
| 부품 이름, 조립 계층(어느 조립품 아래), 부품 수 · 같은 부품 개수 | ✅ 지금 | STEP의 제품 이름과 조립 관계를 읽는다 |
| 부품별 치수(x · y · z), **두께**(가장 얇은 치수) | ✅ 지금 | 조립 규칙의 값 계산에 이미 쓴다 |
| 체적, 질량 추정(체적 × 밀도) | 🟡 | 체적은 계산한다. 열린 모델은 추정값이 되므로 **추정 표시**. 밀도는 재료가 정해져야 한다 |
| 위치, 분리 방향, 맞닿은 부품, 체결 부품(볼트 · 링) 탐지 | ✅ 지금 | 조립 순서와 단계 나누기에 쓴다 |
| 이름 속 규격(`M3`, `×12`) | ✅ 지금 | 이름에 있을 때만. `threadSize` · `length` 후보로 구조화한다 ([attribute-extraction.md](attribute-extraction.md)) |
| 재료, 표면처리, 색 | ⬜ | 대부분의 STEP 파일에 없다. 있으면 읽는다(AP242 등) |
| 공차, 표면 거칠기, 용접 기호, 나사 상세(피치) | ⬜ | 제품 제조정보(PMI)가 파일에 들어 있어야 한다. 없으면 사양서 · 도면에서 와야 한다 |
| STL · OBJ · GLB | 🟡 | 이름 · 계층이 없는 하나의 모양이라 **치수만** 가능 |

### 사양서(PDF · TXT)에서

| 속성 | 상태 | 비고 |
|---|---|---|
| 부품 · 조립품에 관련된 **근거 구절** 찾기 | ✅ 지금 | 문장 조각을 점수로 찾아 연결한다. 정의 · 조립 · 분해 절차 구절 |
| 한글 이름과 설명 | 🟡 | AI를 연결했을 때 선택 기능 |
| 값 추출: 토크(0.6 N·m), 재료(SUS304), 치수, 규격 | ⬜ | 숫자+단위 패턴으로 **후보**를 뽑고 사람이 확정하는 흐름이 필요. 판정은 OPMS의 추출 · 검증 파이프라인을 **재사용**하는 쪽이 낫다 |
| 표 안의 값 | ⬜ | PDF 표는 글자 위치가 깨지기 쉽다. 표 인식이 필요 |
| 스캔본 | ⬜ | 글자 인식(OCR) 필요 |

### BOM 시트(xlsx · csv)에서

| 속성 | 상태 | 비고 |
|---|---|---|
| 품번 · 수량 · 도면 번호 | ⬜ | 열 이름 규칙을 정하면 쉽다. 품번이 일치하면 자동 확정 |
