## 1. 배경과 문제

설계 변경은 부품 하나를 바꾸는 일로 끝나지 않는다. 같은 부품이 여러 BOM에 쓰이고, 그 BOM으로 작업지시가 나가고, 부품은 이미 발주돼 있거나 창고에 있다.

- 바꾼 부품이 **어느 제품 · BOM · 작업지시 · 발주 · 재고**에 걸리는지 사람이 엑셀과 기억으로 찾는다. 빠뜨리면 구형 부품이 계속 조립된다.
- 반대로 **"영향이 있다"를 곧 "바꿔야 한다"로 읽는** 실수도 잦다. 이미 만든 제품은 기존 사양으로 허용될 수 있고, 진행 중 작업은 별도 검토가 필요하며, 남은 재고를 쓸지 격리할지는 승인 판단이다.
- 체결 부품은 **짝이 맞아야** 한다. 너트를 바꾸면 볼트와 나사 규격 · 피치가 맞는지, 판이 두꺼워지면 볼트 길이가 충분한지 다시 따져야 한다.
- 지금 PDM에는 설계 변경에 쓸 자리가 `item_revision.change_note`(글 한 칸) 하나뿐이고, `where_used`(역전개)만 있다. 발주 · 작업지시 · 재고 · 변경 요청 · 적용 범위는 PDM에도 OPMS에도 없다.

> 참고: SAP도 진행 중인 생산오더를 무조건 자동 변경하지 않고 **통제된 변경 절차**로 다룬다(learning.sap.com). 이 PRD의 "영향 ≠ 변경" 원칙과 같은 취지다.

## 2. 목표와 비목표

### 목표
1. **변경 요청**을 이유 · 이전 조건 · 이후 조건 · 승인 상태와 함께 기록한다.
2. 변경 대상 개정에서 출발해 **사용 BOM → 제품 → 작업지시 → 발주 · 재고**로 영향 대상을 찾아간다.
3. 변경 뒤의 BOM을 가상으로 펼쳐 **볼트 · 너트 · 와셔의 짝과 그립 길이를 다시 판정**한다.
4. 영향 발견과 **처분 결정을 분리**한다. 대상마다 "그대로 허용 · 재작업 · 격리 · 취소 …"를 사람이 정하고 승인한다.
5. 적용 범위를 **날짜뿐 아니라 사업장 · 생산 로트 · 제품 일련번호**로 표현한다.
6. OPMS 품번(`:Part`) 위에 개정 · BOM · 변경 객체를 얹되, **온톨로지 버전을 부품 개정으로 대신하지 않는다**.

### 비목표 (이번 범위 밖)
- ERP · MES 쪽 데이터를 **고치거나 자동으로 변경 지시를 내리는 것**. PDM은 영향과 처분 결정을 **기록하고 내보내기까지만** 한다(F-CHG-8). 발주 변경 · 작업지시 변경은 ERP · MES의 일이다.
- 구매 · 재고 · 원가 계산, 설비 제어 (ERP · MES의 일 — [PRD.md](PRD.md) 2장과 같다)
- OPMS 부품 마스터 · 분류체계 · 짝 규칙의 **수정**(OPMS 소유, PDM은 읽기만 한다)
- 새 부품 품번 발급과 OPMS 등록 요청(2026-11-11 사용자 지시로 삭제된 범위)
- 다단 결재, 인증 체계 (당분간 1단계 승인과 데모 사용자)

## 3. 사용자와 대표 시나리오

| 사용자 | 하는 일 |
|---|---|
| 설계 엔지니어 | 변경 요청을 만들고 이전 · 이후 조건을 적는다. 영향 목록을 보고 보완한다 |
| 구매 담당 | 미입고 발주 · 재고 항목의 처분을 제안한다(유지 · 변경 · 취소 · 격리 · 반품) |
| 생산기술 · 생산 담당 | 진행 중 · 미착수 작업지시의 처분과 적용 범위(로트 · 일련번호)를 검토한다 |
| 승인자 | 영향 · 처분 · 적용 범위를 보고 변경을 승인한다. 승인되면 새 개정이 발행된다 |

**시나리오 SC-1: 너트를 바꾼다** — 설계가 `BRK-M8`의 육각너트 P-00000000022(피치 1.25)를 P-00000000023(M8 **가는나사, 피치 1.0**)으로 바꾸자고 요청한다 → 시스템이 변경 뒤 BOM에서 볼트(피치 1.25)와 너트(피치 1.0)가 **짝이 맞지 않음**을 찾아 막는다 (그립 길이는 새 너트 높이 6.8 mm가 같아 28.5 mm로 통과한다. 이 시연 DB의 `P-…23`에는 `nutHeight`가 있다) → 영향 목록에 이 BOM을 쓰는 작업지시와 미입고 발주가 함께 나온다.

**시나리오 SC-2: 상판이 두꺼워진다** — 상판 브래킷을 8 mm에서 12 mm로 바꾼다 → 필요 볼트 길이가 28.5 mm에서 32.5 mm가 돼 현재 볼트(30 mm)가 **2.5 mm 모자란다** → 대체 후보(플랜지볼트 M8×40)를 보이되 "조합을 바꿔야 해서 조건부"라고 알린다 → 이미 조립한 제품은 기존 사양을 허용할지 승인자가 정한다.

**시나리오 SC-3: 바뀐 것이 개정인가 교체인가** — 볼트의 도면 공차가 바뀌면 같은 품번의 **새 개정**이고, 볼트 재질이나 길이가 바뀌면 OPMS에서 **다른 품번**이다(OPMS는 규격으로 부품을 구분한다). 시스템은 변경 종류를 고르면 어느 쪽인지 안내한다.

## 4. 목표 제품: `BRK-M8` "M8 체결 브래킷 모듈"

볼트와 너트(와셔 포함)로 판 두 장을 체결하는 가장 단순한 제품이다. 이 저장소의 `neo4j/sample.cypher`에 이미 있는 M8 체결 세트(개정 R00→R01 "너트 · 와셔 추가")와 OPMS 시드 부품이 그대로 맞는다.

| 구성 | 수량 | 출처 | 핵심 속성 |
|---|---|---|---|
| 상판 브래킷 (가공품) | 1 | PDM 품목. OPMS `:Part` 없음 | 두께 8 mm |
| 하판 브래킷 (가공품) | 1 | PDM 품목. OPMS `:Part` 없음 | 두께 8 mm |
| **체결 세트** (조립품) | 1 | PDM 조립품 | |
| ㄴ 육각볼트 M8×30 `P-00000000001` | 4 | OPMS HexBolt | 피치 1.25, SUS304, A2-70 |
| ㄴ 육각너트 M8 `P-00000000022` | 4 | OPMS HexNut | 피치 1.25, SUS316, A4-80, 높이 6.8 mm |
| ㄴ 평와셔 M8 `P-00000000025` | 8 | OPMS FlatWasher | 두께 1.6 mm, SUS304 |

- 와셔는 볼트 하나당 2개(머리 밑 1 · 너트 밑 1)다.
- 두께 · 판 구멍은 PDM CAD 분석이 읽은 값(추정 표시)이거나 사람이 확정한 값이다.
- OPMS에는 조립품 · 가공품 분류가 없어 판 두 장과 조립품은 `:Part` 없이 PDM 품목으로만 둔다. 이 예외는 11장 열린 질문 3이다.
- 실제 STEP 파일은 저장소에 없다. 이 제품의 3D는 시험용 형상 생성기(`boltMesh` · `nutMesh` · `washerMesh`)나 새로 만든 파일로 보인다. 저장소 밖의 HCR 로봇 STEP은 볼트만 있고 너트가 없어 맞지 않는다.

## 5. 시스템 경계와 데이터 소유

```
              ┌────────── Onto PDM ──────────┐          ┌──── OPMS ────┐
변경 요청 ───▶│ 변경 객체 · 영향 탐색 · 처분 │─ 읽기 ──▶│ :Part · 분류  │
              │ 개정 · BOM(ItemRevision)      │◀ 속성 ──│ 짝 규칙 · 버전│
              └───────▲───────────────┬──────┘          └──────────────┘
         읽기 사본 feed │               │ 승인된 변경 · 처분 목록 (내보내기)
              ┌───────┴───────┐       ▼
              │  ERP · MES    │   설계 · 구매 · 생산 담당이 후속 업무를 한다
              │ 발주·작업지시·재고│
              └───────────────┘
```

| 데이터 | 소유 | 비고 |
|---|---|---|
| 품번 · 분류 · 속성 · **짝 규칙** · 온톨로지 버전 | **OPMS** | PDM은 읽기만. OPMS에는 부품 개정 · BOM · 발주 · 재고 · 작업지시 · 변경 요청이 **코드로 없다**(설계 문서에만 일부) |
| 품목 · 개정(`ItemRevision`) · BOM(`CONTAINS`) | PDM | 기존. 승인본은 DB 트리거로 불변이라 변경은 **새 개정**을 만든다 |
| 변경 요청 · 변경 대상 · 영향 발견 · 처분 · 적용 범위 · 검토 | **PDM (새)** | [change-impact-ontology.md](change-impact-ontology.md) |
| 발주 항목 · 작업지시 · 재고 로트 | **ERP · MES** (PDM은 읽기 사본) | `source_system` · `as_of`를 항상 같이 둔다. 기존 `inventory_balance` 방식을 따른다 |

> 연결 원칙: OPMS 쪽을 고치지 않는다. OPMS에 있는 것은 읽고, 필요한 것은 요청서로 부탁한다(11장 5, [neo4j-lpg-design.md](neo4j-lpg-design.md) 6장).

## 6. 업무 흐름

```
변경 요청 → 영향 대상 탐색 → 설계 · 구매 · 생산 검토 → 적용 시점 · 대상 결정 → 승인 → 후속 업무 반영
```

| 단계 | 하는 일 | 주요 객체 |
|---|---|---|
| 변경 요청 | 이유, 이전 · 이후 조건, 변경 종류(교체 · 개정 · BOM 편집 · 속성 변경) | `ChangeRequest` · `ChangeTarget` |
| 영향 탐색 | 대상 개정 → 사용 BOM → 작업지시 → 발주 · 재고를 찾는다. 체결 짝 · 그립 길이를 다시 판정한다 | `ImpactFinding` |
| 검토 | 설계 · 구매 · 생산이 각자 대상별 의견을 낸다 | `Disposition` 제안 |
| 적용 결정 | 대상마다 처분과 **적용 범위**(유효일 · 사업장 · 로트 · 일련번호)를 정한다 | `Disposition` · `ApplicabilityScope` |
| 승인 | 승인자가 확정한다. 확정되면 **새 개정이 발행**된다 | `ChangeOrder` |
| 후속 반영 | 처분 목록을 내보내고 그래프에 발행한다. ERP · MES 변경은 각 담당이 한다 | 내보내기 · outbox |

핵심 연결: **변경 대상 개정에서 사용 중인 BOM → 관련 작업지시 → 발주 · 재고**를 찾아간다.

## 7. 기능 요구사항 (F-CHG)

| ID | 요구 | 우선 | 상태 |
|---|---|---|---|
| F-CHG-1 | **변경 요청 등록**: 이유, 이전 · 이후 조건, 변경 종류, 대상(품목 · 개정 · BOM 줄), 상태(작성 → 영향 확인 → 검토 → 승인 · 반려) | P0 | 🟡 요청 · 지시 · 대상 · 상태 전이(`can_transition`) · API · 웹 ✅, **저장은 메모리**(PG 표는 SQL만). 변경 종류는 `replace · revise · bom_edit · attribute_edit` |

| F-CHG-3 | **외부 객체 연결**: BOM 개정 → 작업지시(적용 BOM · 공정 개정, 진행 상태) → 발주 항목(품번 · 개정 · 미입고 수량) → 재고 로트 | P0 | 🟡 작업지시 → 발주 → 재고 로트 영향 ✅(픽스처로 확인). 실제 ERP · MES 데이터는 없다 |

OPMS가 판정 API를 열면 교체. 입력(판 두께 · 체결 구성)을 넣는 API · 화면은 없음 |

| F-CHG-6 | **적용 범위**: 유효일 · 사업장 · 생산 로트 범위 · 제품 일련번호 범위. 범위가 겹치는지 판정하고, 영향 대상이 범위 안인지 표시한다 | P0 | 🟡 범위 판정(`inside · outside · partial · unknown`) · 겹침(`SCOPE_OVERLAP`) ✅. **로트는 목록으로**만, 로트 번호 체계 미정이면 `unknown`. 날짜 · 일련번호 · 사업장 중 하나라도 밖이면 범위 밖 |

PG 쪽 `approve_change_order`(원자성 · 불변 시험 통과)는 백엔드에 연결 안 됨. 필요한 검토는 design 항상 · purchasing/production은 해당 영향이 `affected`일 때 — 자격은 역할로 갈음 |
| F-CHG-8 | **후속 업무 반영**: 승인된 처분 목록을 내보내고 그래프에 발행한다. **ERP · MES에 쓰지 않는다** | P1 | 🟡 내보내기 `GET /changes/{id}/export` ✅(승인된 건만). 그래프 발행은 ⬜(발행기 없음) |
| F-CHG-9 | **영향 3D 그래프**: 변경 대상 · 영향 노드 · 처분을 연결 그래프(3D)와 목록으로 보인다. 기존 `Graph3D` 재사용 | P1 | ✅ 3D + 목록 대안, 심각도는 색 · 아이콘 · 글자. 백엔드 `GET /changes/{id}/impact/graph` |
| F-CHG-10 | **온톨로지 버전 ≠ 부품 개정 가드**: 온톨로지 버전이 바뀌면 영향받는 부품을 **읽기 보고(`OntologyImpact`)** 로만 알리고, 부품 개정을 만들지 않는다 | P0 | 🟡 가드 ✅(규격이 바뀌는 `revise`는 422 `REVISION_CHANGES_IDENTITY`, `ontology` 종류 대상 불가, DB CHECK). `OntologyImpact` **계산**은 ⬜ |
| F-CHG-11 | **감사 · 판단 시점 스냅샷**: 영향 발견마다 어느 온톨로지 버전 · 규칙 · 외부 데이터 시각(`as_of`) · 임시 판정 여부를 남긴다. 나중에 같은 변경을 다시 열어도 "그때 무엇을 보고 결정했는지" 재현된다 | P0 | 🟡 `impact_run`/`impact_finding`에 온톨로지 버전 · 규칙 · `as_of` · 임시 여부 · 입력 해시 · stale 사유 ✅. 감사 기록은 메모리 수준 — PG `audit_log` 트리거는 SQL만 |
| F-CHG-12 | **외부 데이터 입력 경로**: 발주 · 작업지시 · 재고 로트를 ERP · MES에서 받는 입구(읽기 전용 사본). 형식은 11장 열린 질문 1 | P0 | 🟡 `POST /feeds/work-orders · purchase-order-lines · stock-lots` ✅(`X-PDM-Feed-Token` = `PDM_FEED_TOKEN`, 늦은 `as_of` 무시, 행별 결과). **형식은 임시**, 실제 ERP · MES 연결 없음. 새 feed가 오면 열린 지시의 최신 분석은 stale |

## 8. 판정 원칙 (OPMS와 PDM의 역할)

OPMS가 판정 규칙의 주인이라는 원칙([fit-check-plan.md](fit-check-plan.md))을 유지한다. 다만 지금 OPMS가 주는 것은 제한적이다.

| 판정 | OPMS 현황 (`PDM` 브랜치) | 이 기능에서의 처리 |
|---|---|---|
| 볼트 길이 ≥ 홈 깊이 + 2.0 mm | `POST /api/v1/fit/judge`(A-42)에 있음. 4상태(ok · conditional · no · unknown). **시연용 가정, 담당자 미지정**(`rules.yaml:178-187`) | 탭 구멍용이다. 관통 체결(볼트+너트)에는 쓰지 않는다 |
| 볼트↔너트↔와셔 짝 | `mates_with` 규칙(나사 규격 + 피치)이 온톨로지에 있고 판정은 계산형. **서버 판정 API 없음**, 결정 5에서 "하지 않음" | PDM이 OPMS 스냅샷의 규칙 명세를 읽어 **같은 4상태 의미**(fits · mismatch · unknown · unrelated)로 계산하고 `temporary: true`로 표시 |
| **그립 길이**(관통 체결) | **없음** | PDM **참고 판정**으로 계산한다. OPMS 규칙이 아님을 화면에 밝힌다. 공식은 아래 |
| 강도등급(A2-70 · 10 …) | 값만 있고 **순서 비교가 없다**(`CR-NEXT-mating-rules.md:233`) | 판정하지 않고 **"검토 필요"** 로만 표시 |
| `POST /parts/match` | 보류(중복 부품 찾기용이라 이 일과 다르다) | 쓰지 않는다 |

**그립 길이 공식 (시연용 가정이다. 기준 출처 · 담당자 미지정 — OPMS의 홈 깊이 여유 값과 같은 성격):**

```
필요 볼트 길이 = Σ 판 두께 + (와셔 두께 × 볼트 하나당 와셔 수) + 너트 높이(nutHeight) + 2 × 피치
```

| 경우 | 계산 | 판정 |
|---|---|---|
| `BRK-M8` 기준(R00) | 8 + 8 + 1.6×2 + 6.8 + 2×1.25 = **28.5 mm** ≤ 볼트 30 mm (여유 1.5) | 통과 |
| SC-2(상판 12 mm) | 8 + 12 + 3.2 + 6.8 + 2.5 = **32.5 mm** > 30 mm (**2.5 mm 부족**) | 실패 |

입력이 CAD 추정값이면 판정을 **한 단계 낮춰** 보이고(OPMS 규칙과 같은 방식) "실물로 확인하세요"를 붙인다. OPMS가 짝 판정 API나 그립 길이 규칙을 열면 PDM은 임시 계산을 걷고 그 판정을 그대로 쓴다. 이를 위해 OPMS에 부탁할 요청서가 11장 5에 있다.

## 9. 비기능 요구

| 영역 | 요구 |
|---|---|
| **가짜 데이터 없음** | 화면에 목(mock) 데이터를 넣지 않는다(2026-11-11 사용자 지시). 데이터가 없으면 "OPMS에 연결되면 표시돼요" 같은 안내만 보인다. 시연 · 시험은 시험 픽스처로 격리하고 `source_system='fixture'`로 표시한다 |
| 정확성 | 영향 목록은 **결정적**이다. 같은 입력 · 같은 외부 `as_of`면 같은 결과. 외부 데이터가 새로 오면 이전 결과를 **낡음(stale)** 으로 표시 |
| 추적성 | 판단 시점의 온톨로지 버전 · 규칙 · 입력값 · 임시 여부를 남긴다(F-CHG-11) |
| 불변 | 승인된 개정은 고치지 않는다. 변경은 새 개정으로 |
| 권한 | 승인 전 변경 요청은 작성자 · 관리자만. 승인은 승인자 역할. 구매 · 생산 검토 역할 추가는 판단 필요 |
| 디자인 | OPMS 토큰 · 글래스 셸. 빨강은 오류 · 위험에만, 경고는 호박색. 3D 정보는 목록으로도 본다 |
| 시험 | 단위 · DB · 백엔드 · 웹 · 실제 브라우저(E2E). SC-1~SC-3가 수락 시험이다 |
| 성능 | 영향 탐색은 BOM 2,000노드 · 작업지시 1,000건 기준에서 몇 초 안에 끝난다(기준치는 구현 때 확정, 판단 필요) |

병렬로 나눌 수 있는 묶음과 파일 단위 구성은 [change-impact-design.md](change-impact-design.md) 10장에 있다. OPMS와 연결되는 장기 확장이므로 **C0~C4가 첫 시연 범위**(구현됨)이고, C5와 PG 저장소 연결은 OPMS · ERP · MES와의 협의가 있어야 한다.

## 11. 열린 질문 (결정이 필요)

결정 상태: **[가정으로 진행]** 제가 제안값으로 정하고 구현했다 — 사용자가 뒤집으면 바꾼다 · **[사용자 결정 대기]** 정해지지 않았다 · **[구현의 현재 동작]** 정책은 미정이지만 기본 동작이 정해져 있다.

1. **[가정으로 진행: 시험 픽스처 + 읽기 전용 feed 입구]** **발주 · 작업지시 · 재고는 어떻게 들어오나?** ERP · MES에서 파일(CSV · JSON), API, 아니면 아직 미정인가? (BOM 가져오기가 삭제된 범위와 다른 일인지도 확인 필요.) 제안: 처음에는 **시험 픽스처 + 읽기 전용 feed 입구**만 두고 형식은 ERP · MES가 정해지면 맞춘다.
2. **[사용자 결정 대기(현장 확인)]** **영향 대상별 처분의 기본값**은? 아래 제안을 현장 책임자가 확인해야 한다. 구현의 선택지는 대상 종류별로 정해져 있고 기본 제안은 칩으로만 보인다(미리 채우지 않는다).

   | 영향 대상 | 제안 기본 처분(자동 변경 아님) |
   |---|---|
   | 이미 생산한 제품 | 기존 사양 허용 (승인자 사유 필요) |
   | 진행 중 작업 | **별도 변경 검토 필수** — 계속 · 재작업 · 중단 중 선택 |
   | 미착수 작업 | 새 개정 적용 |
   | 미입고 발주 | 유지 · 변경 · 취소 중 선택 (구매 담당) |
   | 재고 | 계속 사용 · 격리 · 반품 중 선택 |
3. **[가정으로 진행: PDM 품목만 두고 "OPMS 미등록"으로 표시]** **가공품 · 조립품은 OPMS `:Part` 없이 PDM 품목만 두어도 되나?** 현재 그래프 검사(`item_one_part`)는 모든 품목에 `:Part`를 요구한다. 예외를 두거나, OPMS에 조립품 분류를 부탁한다([neo4j-lpg-design.md](neo4j-lpg-design.md) 6장).
4. **[가정으로 진행: 시연용 가정 — 화면에 "PDM 참고 판정 · 기준 미지정"으로 표시]** **그립 길이 공식의 기준과 담당자**는? 나사 끝 여유(`2 × 피치`)와 와셔 수는 시연용 가정이다.
5. **[사용자 결정 대기: 초안은 `docs/opms-request-change-impact.md`, 전달 전]** **OPMS에 부탁할 것**: ① 짝 판정 엔드포인트(`mates_with` 서버 판정) ② 관통 체결 그립 길이 `fit_check` 규칙 ③ `strengthGrade` 순서 비교 ④ 조립품 · 가공품 분류. OPMS는 팀 저장소라 별도 브랜치 · PR이 필요하고 OPMS 쪽 담당자는 미확인이다. 요청서 초안 6건을 썼다(전달 여부 · 시점은 사용자 결정).
6. **[구현의 현재 동작: design 검토는 항상, purchasing/production은 해당 영향이 `affected`일 때 필요. 자격은 역할로 갈음 — 사용자 결정 대기]** **작업지시 · 발주 판단을 누가 승인하나?** 승인자 1명인가, 구매 · 생산 담당의 병행 승인인가?
7. **[가정으로 진행: 시험용 생성 형상]** **실제 CAD**: `BRK-M8`을 시험용 생성 형상으로 시연해도 되나, 아니면 실제 STEP을 받을 수 있나?
8. **[사용자 결정 대기 — 구현의 현재 동작은 **막는다**: `blocked`가 남으면 승인 불가, `blocked`에 `accept_risk`도 422]** **`blocked`를 사유를 적고 예외 승인할 수 있게 할까?** 기본은 막는다(안전 · 품질 정책이라 현장 합의 필요, [worker-view-proposal.md](worker-view-proposal.md) 4장 질문 2와 같은 성격).
9. **[구현의 현재 동작]** **볼트 규격 변경 때 새 품번이 OPMS에 없으면?** PDM은 등록 요청을 보낼 수 없다(삭제된 기능). "후보 없음 — OPMS에 등록 필요"로 안내만 한다.
10. **[사용자 결정 대기]** **임시 짝 판정을 OPMS가 서버 판정을 열 때까지 유지해도 되나?** OPMS 문서(`CR-NEXT-part-relation-rule.md:151`)는 "PDM이 규칙을 직접 읽어 계산하지 않는다(두 곳 구현 방지)"라고 한다. 지금 PDM의 임시 계산은 이 원칙과 어긋난다. 요청서 1에 밝혀 두었고, 결과에는 항상 `temporary: true`가 붙는다.
11. **[사용자 결정 대기]** **진행 중 작업지시가 범위 밖이면 영향 목록에서 빼도 되나?** 구현은 날짜 · 일련번호 · 사업장 · 로트 중 **하나라도 명확히 밖이면 범위 밖**으로 보고 영향 목록에서 뺀다. 그래서 SC-2에서 `WO-FX-0002`(진행 중, 일련번호 51~80)는 일련번호만 보면 71~80이 겹치지만 **시작일(2026-11-02)이 효력일(2026-12-01)보다 앞서** 범위 밖이 되어 목록에 나오지 않는다. 사용자 자료의 "진행 중 작업은 별도 변경 검토가 필요하다"와 맞추려면 이 경우를 `review`로 남길지 정해야 한다.
12. **[사용자 결정 대기]** **판 두께 · 체결 구성(어느 판을 어떤 볼트 세트가 조이는지)은 누가 어디서 입력하나?** 엔진의 입력인데 지금은 시험 픽스처와 DB 표로만 들어가고 API · 화면이 없다. 제안: 처음에는 수동 입력 화면, CAD 탐지로 만든 초안은 나중([개발 설계 10.3](change-impact-design.md) 7번).

## 부록 A. 용어와 객체 대응

사용자가 정리한 업무 객체를 이 시스템의 라벨로 옮기면 다음과 같다(상세: [change-impact-ontology.md](change-impact-ontology.md)).

| 업무 객체 | 이 시스템 | 소유 | 비고 |
|---|---|---|---|
| 변경 요청 · 지시 (ChangeRequest/Order) | `ChangeRequest` · `ChangeOrder` | PDM (새) | 변경 이유, 이전 · 이후 조건, 승인 상태 |
| 부품 개정 (PartRevision) | 기존 `ItemRevision` | PDM | 개정별 사양과 승인 상태. **온톨로지 버전이 아니다** |
| BOM 개정 · 항목 (BOMRevision/Line) | 조립품의 `ItemRevision` + `CONTAINS` 관계 | PDM | 부품 개정, 수량, 단위, 적용 위치 |
| 발주 항목 (PurchaseOrderLine) | `PurchaseOrderLine` | ERP (PDM 읽기 사본) | 품번 · 개정, 미입고 수량 |
| 작업지시 (WorkOrder) | `WorkOrder` | MES (PDM 읽기 사본) | 적용 BOM · 공정 개정, 진행 상태 |
| 재고 | `StockLot` | ERP · MES (PDM 읽기 사본) | 로트 · 사업장 |
| 영향 · 처분 · 적용 범위 | `ImpactFinding` · `Disposition` · `ApplicabilityScope` | PDM (새) | "영향이 있다"와 "변경해야 한다"의 분리 |

OPMS 설계 문서에는 미구현 `:PartRevision` · `:BomLine` · `:Product`가 있다. 이름이 겹치지 않게 PDM은 기존 `ItemRevision` · `CONTAINS`를 쓴다. OPMS가 이 객체들을 구현하면 연결 방법을 다시 정한다.

## 부록 B. 이번 조사에서 확인한 사실과 한계

- 읽은 것: OPMS `PDM` 브랜치 `03331ba`(온톨로지 0.19.0, 커밋 `58ffed2`). 이 PC의 OPMS Neo4j(0.19.0)는 **읽기 전용으로 실제 조회**했다.
- OPMS에는 `HexBolt` · `HexNut` · `FlatWasher` 클래스와 M8 시드 부품이 있다. 개발 DB에서 확인한 값: 볼트 `P-…01`(M8 · 길이 30 · 피치 1.25 · A2-70 · SUS304), 너트 `P-…22`(`nutHeight` 6.8 · 피치 1.25 · A4-80 · SUS316), 너트 `P-…23`(`nutHeight` 6.8 · 피치 **1.0** · A2-70 · SUS304), 와셔 `P-…25`(두께 1.6 · SUS304). `P-…15`는 개발 DB에 `HexFlangeBolt` M8로 있으나 길이 · 재질은 **확인하지 못했고** 시험은 OPMS YAML 값을 쓴다. `headType` · `strengthClass`는 현재 온톨로지에 없고 강도는 `strengthGrade`(글자)다.
- 스냅샷 `rules`에 `bolt_nut` · `bolt_washer` · `nut_washer`와 `substitutes` 규칙이 있는 것을 확인했다.
- 시험: 백엔드 518 · 웹 512 · DB(PGlite) 33개 통과. 이전 판에 "너트 `P-…23`에 `nutHeight`가 없다"고 쓴 것은 YAML 시드 기준이었고 **실제 DB에는 6.8이 있다**(SC-1의 그립 길이는 통과). 값이 비어 있는 너트로 `unknown`(`value_missing`)이 나오는 경우는 별도 시험 케이스다.
- "필요 길이 = 두께 + 너트 높이 + 여유" 공식은 이 저장소와 OPMS 어디에도 없다. 8장의 공식은 이 문서가 처음 제안하는 가정이다.
